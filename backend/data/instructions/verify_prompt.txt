## CATEGORY-SPECIFIC VERIFICATION RULES

### reentrancy
Verify ALL five conditions from the actual code:
  1. Is the call to msg.sender or a variable (not hardcoded) address?
  2. Does it use .call{value:…}() — not .transfer() or .send()?
  3. Is a critical state variable updated AFTER the call?
  4. Can a public/external function be re-entered during the call?
  5. Is there NO reentrancy guard?
If ALL five hold → confirm. If any is clearly absent → score accordingly.

### arithmetic
TWO CASES — read the pragma version in the contract:
  CASE A (pragma < 0.8.0): Overflow IS real. Confirm if no SafeMath and no bounds check.
  CASE B (pragma >= 0.8.0): Confirm ONLY if inside explicit `unchecked {}` block.
Do not reject pre-0.8.0 arithmetic findings without strong justification.

### unchecked_low_level_calls
Verify whether the return value is actually checked after the call.
Look carefully — the check may appear on a nearby line. If truly unchecked → confirm.

### access_control
OLD CONSTRUCTOR PATTERN: Verify the function name vs the contract name. If different
name sets owner or initialises state → confirm. Look for any modifier or require(owner).

### bad_randomness
Confirm if ANY block property determines a game, lottery, prize, or random selection outcome.
Read the full function that uses the block property — trace where the value goes.
Score 0.00 only if the block property is provably used for logging with no financial effect.

### time_manipulation
Verify: does block.timestamp actually control a financial outcome (deadline, cooldown, prize)
where a miner could gain by ±15 seconds? If yes → confirm.

### denial_of_service
Verify: is there a loop a user can extend? Can ETH failure actually block the whole function?
If a realistic blocking path exists in this code → confirm.

### front_running
Verify: can a mempool observer actually gain advantage? Is outcome determined by call order?
Lean toward confirming if any realistic ordering advantage exists.

### other
Look at what exploitable mechanism the finding describes.
If the contract code confirms it can occur → confirm or uncertain.

## CATEGORY-SPECIFIC SKEPTICAL RULES

### reentrancy
Reject if ANY of these is true:
  - .transfer() or .send() is used (gas-limited, cannot reenter)
  - State is updated BEFORE the external call (checks-effects-interactions is followed)
  - A reentrancy guard is present (nonReentrant, locked, mutex)
  - The call is to a fixed trusted address, not msg.sender or a variable
Confirm only if ALL five classic conditions hold: external call to variable address, .call{value}(),
critical state updated AFTER, re-enterable public function, no guard.

### arithmetic
TWO CASES — check the pragma version in the contract first:
  CASE A (pragma < 0.8.0): Overflow IS real. Score 0.80+ if no SafeMath and no bounds check.
  CASE B (pragma >= 0.8.0): Built-in protection. Score 0.00 UNLESS inside explicit `unchecked {}`.
The `unchecked` keyword does NOT exist in Solidity < 0.8.0.

### unchecked_low_level_calls
Reject if the return value IS checked (stored in a variable, tested with require/if).
Confirm if the return value is completely ignored on the same line.

### access_control
OLD CONSTRUCTOR PATTERN (Solidity < 0.4.22): If a function has a DIFFERENT name than
the contract but sets owner or initialises critical state → confirm at 0.85.
Reject if the function is protected by a modifier or require(msg.sender == owner/admin).

### bad_randomness
Confirm if ANY block property (block.timestamp, block.number, block.difficulty, blockhash,
block.coinbase, block.prevrandao, keccak256 of block data) is used to determine:
  - a winner, prize, or selection
  - a random number or seed passed to another function
  - a lottery or game outcome
Score 0.00 ONLY if the block property is provably used only for logging or event emission,
with no effect on any financial or game outcome. Read the full function body before deciding.

### time_manipulation
Confirm if block.timestamp is the PRIMARY factor for a financial decision where a miner
could gain by manipulating it by ±15 seconds (deadline expiry, cooldown bypass).
Score 0.00 if timestamp is used only for logging or where ±15s drift has no exploitable effect.

### denial_of_service
Confirm if a loop iterates over a user-extendable array, or ETH is sent inside a loop
where a single revert blocks all others.
Score 0.00 if gas concerns are theoretical with no realistic blocking path in this code.

### front_running
Confirm if a mempool observer can gain advantage by ordering transactions (commit-reveal,
first-caller-wins, ERC-20 approve+transferFrom race).
Score 0.00 if the outcome is deterministic regardless of transaction ordering.

### other
Score 0.40+ if the code confirms an exploitable mechanism exists, even if unclear category.
Score 0.00 only if the described condition clearly cannot occur in this code.

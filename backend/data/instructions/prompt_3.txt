## VULNERABILITY KNOWLEDGE BASE & VALID CATEGORIES
You MUST choose exactly ONE category per finding from the list below. Do NOT invent new categories. Evaluate the code strictly against these definitions and attack scenarios:

### 1. Reentrancy (SWC-107)
Also known as race to empty, recursive call vulnerability. Occurs when external contract calls are allowed to make new calls to the calling contract before the initial execution is complete.
* **Detection:** Look for state changes occurring *after* a low-level call (`call.value()()`) or external address interaction.
* **Attack Scenario:** Victim executes low-level call to send Ether before updating balances. The malicious contract's fallback function catches the funds and calls back into the victim's withdraw function again, successfully withdrawing multiple times before the balance is ever updated.
* **STRICT RULES — ONLY report if ALL conditions hold:**
  * (1) External call to msg.sender OR untrusted address (NOT to a fixed trusted address like an oracle or owner)
  * (2) Call must be `.call()` with value transfer — NOT regular `.transfer()` or `.send()` (those are safe in 0.8+)
  * (3) State change AFTER the call, not before (checks-effects-interactions violated)
  * (4) State change is security-critical (affects balances, allowances, ownership)
  * (5) There exists a callable public/external function that can re-enter during the call
* **DO NOT REPORT if:**
  * State is checked/updated BEFORE the call
  * Call is to a fixed trusted address (e.g., `owner.call()` where owner is immutable/constant)
  * Reentrancy guard prevents re-entry (e.g., `require(!locked)` or OpenZeppelin ReentrancyGuard)
  * Using `.transfer()` (safe) instead of `.call()` with value
  * External call is to a known safe library or verified pattern

### 2. Access Control (SWC-105/106)
Top OWASP vulnerability. Occurs when insecure visibility settings or bypassed authorization allow attackers to access private values or logic. 
* **Detection — LOOK FOR patterns:**
  * `public function` that should be `onlyOwner` or `onlyAdmin` (e.g., `withdraw()`, `setPrice()`, `transfer()`)
  * `initialize()`, `init()`, `setup()` functions left unprotected (callable multiple times)
  * Functions using `require(msg.sender == owner)` but owner can be changed by attacker
  * Missing visibility modifiers (defaults to `internal` in old Solidity, `public` in newer)
  * `delegatecall` to untrusted contract or user-controlled address
  * Use of `tx.origin` for authorization (vulnerable to phishing)
  * State variables that should be immutable but are mutable (e.g., protocol fees, addresses)
  * Lack of access control on critical functions (mint, burn, pause, upgrade, etc.)
* **Attack Scenario:** An `initialize()` function sets the owner but is left public. After deployment, an attacker calls it to change owner to themselves. Or a `withdraw()` function lacks the `onlyOwner` modifier; attacker calls it to drain funds.
* **DO NOT REPORT if:**
  * Function is intentionally public and this is documented
  * Function is protected by an explicit access control modifier that's correctly implemented
  * Function is part of a public API that's meant to be callable by users

### 3. Arithmetic (Integer Overflow/Underflow) (SWC-101)
Dangerous in Solidity due to the prevalence of unsigned integers. 
* **Detection:** Look for subtraction that can result in negative numbers wrapping to massive positive integers, off-by-one errors in array lengths (`array.length--` without zero checks), or the deprecated `var` keyword limiting loop iterations (e.g., `var` defaulting to `uint8` and infinitely looping if limit > 255).
* **STRICT CONTEXT RULES:**
  * If `pragma >= 0.8.0`: DO NOT report overflow/underflow AT ALL (Solidity 0.8+ has built-in overflow checks)
  * Exception: ONLY report if inside explicit `unchecked {}` block
  * If `pragma < 0.8.0`: ONLY report if arithmetic is UNPROTECTED (no SafeMath, no require checks)
  * If using SafeMath (e.g., `using SafeMath for uint`): DO NOT report `.add()`, `.sub()`, `.mul()` calls
* **DO NOT REPORT:**
  * Simple assignments (e.g., `x = y`)
  * Operations inside `unchecked {}` blocks (intentional wrapping)
  * Division by zero without explicit vulnerability context
  * Operations on constants or fixed values
  * Subtraction with explicit zero checks (e.g., `require(x >= y); return x - y`)

### 4. Unchecked Low Level Calls (SWC-104)
Silent failing sends. `call()`, `callcode()`, `delegatecall()`, and `send()` do not bubble up errors or revert execution upon failure; they just return `false`.
* **Detection:** Look for return values of `.call`, `.send`, `.transfer`, or ERC20 `transfer`/`transferFrom` that are not explicitly checked via `require()`.
* **Attack Scenario:** A contract uses `msg.sender.send(_amount)` to transfer funds, followed by state updates. The receiver is a contract with no payable fallback, so the send fails and returns `false`. Because it is unchecked, the state updates anyway, corrupting the contract's accounting.

### 5. Denial of Service (SWC-113/128)
Gas limit reached, unexpected throw, unexpected kill. Taking a contract offline forever.
* **Detection:** Look for loops over unbounded arrays, forced transfers to untrusted addresses (push over pull), or reliance on external calls that can intentionally revert.
* **Attack Scenario:** An auction contract loops through past bidders to refund them. A malicious bidder is a smart contract that explicitly reverts on receiving funds. When the loop hits the malicious contract, the entire transaction reverts, permanently halting the auction and locking all funds.

### 6. Front-Running (SWC-114)
Time-of-check vs time-of-use (TOCTOU), transaction ordering dependence.
* **Detection — LOOK FOR patterns:**
  * On-chain contest/lottery where first caller or specific order wins (e.g., `if (players.length == 0) winner = msg.sender`)
  * Secrets submitted then verified (answer submission race, flash loan oracle)
  * MEV exploitable: swap price determined by pending transaction state
  * Logic that depends on `tx.gasprice` or transaction ordering
  * Functions that check a condition and execute atomically without metering (check-execute without pause)
  * Rewards/bonuses tied to transaction arrival order or specific `block.number`/`block.timestamp` patterns
  * Commit-reveal schemes without proper time locks (permitting reorg/front-run in same block)
  * State changes that don't use checks-effects-interactions or depend on caller ordering
* **Attack Scenario:** A contract pays out rewards to the first caller in a block. Alice submits txn A. Attacker sees it in mempool, submits txn B with higher gas, miner includes B first, attacker gets reward. Alternatively, a DEX swap price is based on previous block's state; attacker frontruns swap with their own to move price, then backruns to profit.
* **DO NOT REPORT if:**
  * Logic is deterministic and not dependent on transaction ordering (e.g., round-robin using block.number)
  * Proper time-lock or delay mechanisms prevent front-running
  * Function is protected by checks-effects-interactions correctly

### 7. Time Manipulation (Timestamp Dependence) (SWC-116)
Relying on miner-influenced `block.timestamp` or `now` for critical logic.
* **Detection:** Look for `block.timestamp` used in random number generation, precise pricing calculations, or strict access control unlocking.
* **Attack Scenario:** A game pays out the first player at exactly midnight. A malicious miner submits their attempt and artificially sets the block timestamp to exactly midnight, ensuring their block is accepted by the network and they win the prize.

### 8. Bad / Weak Randomness (SWC-120)
Nothing is secret on Ethereum; all blockchain data is public and miner-manipulable.
* **Detection:** CRITICAL: Report ANY use of the following for randomness or decision-making:
  * `block.timestamp` in random assignments (e.g., `nonce = block.timestamp % 10`, `if (block.timestamp % 2 == 0)`)
  * `block.number` in random assignments (e.g., `winner = players[block.number % numPlayers]`, `round = block.number % numRounds`)
  * `block.difficulty` (now `block.prevrandao` in post-merge) used for randomness
  * `blockhash()` for entropy (e.g., `seed = uint(blockhash(block.number - 1))`)
  * Private variables used as seeds (e.g., `uint private seed = block.timestamp + msg.value`)
  * Combining block data in weak hashes (e.g., `keccak256(abi.encodePacked(block.timestamp, msg.sender))`)
  * Lottery/game rolls: `card = deck[block.timestamp % 52]`, `player_index = block.number % players.length`
  * Chainlink VRF or trusted oracle NOT being used
* **Attack Scenario #1 (Prediction):** A lottery uses `winner = uint(blockhash(block.number - 1)) % players.length`. A node operator can predict the blockhash before block inclusion and submit their own ticket for the winning number in advance.
* **Attack Scenario #2 (Reversion):** A game rolls randomness using `uint roll = block.timestamp % 6 + 1`. A malicious contract calls the game, checks if they won (by simulating or reading the outcome), and if they lost, explicitly reverts the transaction. The miner retries with a new block.timestamp until the attack contract wins, then commits the block.
* **DO NOT REPORT if:** Using Chainlink VRF, Randomness Beacon, or other verified oracle

### 9. Short Addresses
Off-chain / Client vulnerabilities resulting from EVM padding incorrectly sized arguments.
* **Detection:** While mostly off-chain, be aware of contracts that do not validate the length of payload data (e.g., expecting a 20-byte address but receiving 19 bytes, causing the EVM to pad with zeroes and shift subsequent arguments, artificially multiplying amounts).

* **Floating Pragma (SWC-103):** ONLY non-fixed compiler version pragma.

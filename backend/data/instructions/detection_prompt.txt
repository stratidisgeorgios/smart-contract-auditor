## MULTI-INSTANCE RULE
If the SAME vulnerability pattern appears in MULTIPLE INDEPENDENT FUNCTIONS, create ONE finding per function.
Do NOT create multiple findings for different call sites within the same function.

Examples:
  - bad_randomness in bet() and spin() → TWO findings (different functions)
  - reentrancy in withdraw() and withdrawAll() → TWO findings (different functions)
  - three .send() calls inside the same checkResult() function → ONE finding for checkResult()
  - unchecked send at line 12 and line 34 in DIFFERENT functions → TWO findings

## ATOMIC REPORTING RULE
Each finding refers to ONE root cause location — one statement or one line.
Do NOT group multiple vulnerability types into one finding.
If multiple DIFFERENT issues exist → create multiple vulnerability objects.

## CATEGORY DETECTION GUIDANCE

### reentrancy  (SWC-107)
Report ONLY when ALL of the following hold:
  1. An external call is made using `.call{value:…}()` to `msg.sender` or an untrusted variable address.
     DO NOT flag `.send()` or `.transfer()` — their 2300-gas stipend prevents re-entry.
  2. A security-critical state variable (balance, ownership, lock flag) is modified AFTER the call, not before.
     If state is updated before the call (checks-effects-interactions followed) → do NOT report.
  3. No reentrancy guard is present (`nonReentrant`, `require(!locked)`, OpenZeppelin ReentrancyGuard).

If suspicious but not certain all three hold → report with confidence: "LOW".

### access_control  (SWC-105/106/115)
Report unprotected withdraw/mint/burn/pause/upgrade functions, `initialize()` callable multiple times,
`tx.origin` used for authentication, unprotected `selfdestruct`/`suicide`,
`delegatecall` to a user-controlled address.

DO NOT report if the function has `onlyOwner`, `onlyAdmin`, or an explicit `require(msg.sender == ...)` guard.

IMPORTANT — OLD SOLIDITY CONSTRUCTOR PATTERN:
In Solidity < 0.4.22, the constructor is a function with the SAME NAME as the contract.
If a function has a DIFFERENT name than the contract AND sets owner or initialises state with no access check → anyone can call it → report as access_control.

### arithmetic  (SWC-101)
- pragma < 0.8.0 → report overflow/underflow if there is no SafeMath and no explicit bounds check.
- pragma >= 0.8.0 → report ONLY if inside an explicit `unchecked {}` block.
Also flag: division before multiplication (precision loss), unsafe casting (e.g. uint256 → uint8).
DO NOT flag arithmetic that is bounded by a prior `require` or `if` check.

### unchecked_low_level_calls  (SWC-104)
Report when the return value of a low-level call is silently discarded.

WHAT TO FLAG:
  - `.call{value:…}()` or `.call(...)` where the return bool is not assigned to a variable.
  - `.send()` where the return bool is not tested in a require/if.
  - ERC-20 `transfer()`/`transferFrom()` (on non-reverting tokens) where the return bool is ignored.

DO NOT FLAG:
  - `.transfer()` — it ALWAYS reverts on failure. There is no return value to check.
  - Any call where `bool success = …` is captured, even if `success` is used conditionally.
  - Any call wrapped in `require(…)` or `if (!result) revert(…)`.

### denial_of_service  (SWC-113/128)
Flag: unbounded loops over user-controlled arrays where an attacker can make the array grow to cause out-of-gas;
ETH sent to addresses inside a loop where one failing recipient can halt the entire loop;
selfdestruct-based forced ETH push that breaks contract logic.
DO NOT flag bounded loops, constant-size iterations, or theoretical gas concerns without a realistic attack vector.

### front_running  (SWC-114)
Flag: first-caller-wins patterns with financial reward; missing commit-reveal in auctions or games;
ERC-20 approve+transferFrom race (no increaseAllowance); functions where knowing the pending tx gives a mempool observer a profit.
Report even if the same line is also covered by another category — a later stage will resolve overlaps.

### time_manipulation  (SWC-116)
Flag: `block.timestamp` (or `now`) used directly for critical decisions — deadlines, cooldowns, or access gates —
where a miner manipulating it by ±15 seconds changes a financial outcome.
Report even if the same line could also be `bad_randomness` — a later stage will resolve overlaps.
DO NOT flag: timestamp used only for logging, event emission, or where ±15s has no exploitable effect.

### bad_randomness  (SWC-120)
Flag EVERY use of `block.timestamp`, `block.number`, `block.difficulty`, `block.prevrandao`, `blockhash()`,
`block.coinbase`, or `keccak256(abi.encodePacked(block.*, ...))` to decide a winner, prize, outcome, or random selection.
Each independent decision point (different function or different require/if branch) is a separate finding.
Report even if the same line could also be `time_manipulation` or `front_running` — a later stage resolves overlaps.
DO NOT flag if Chainlink VRF or a verified randomness oracle is used.

### short_addresses
Flag contracts with public/external functions that accept raw `address` inputs (e.g., `transfer(address to, uint256 value)`)
and perform no length validation on the calldata, making them susceptible to EVM argument-padding exploits.

### other
Use for clearly exploitable issues that do not fit the above nine categories.
When genuinely uncertain whether something is exploitable, report it as "other" with confidence: "LOW".
